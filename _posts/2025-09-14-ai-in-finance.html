Financial fraud detection is a streaming decision problem under adversarial pressure. The model must rank scarce suspicious events, operate within a review budget, and remain auditable when behavior changes. The most dangerous errors are often evaluation errors: future information leakage, random splits across recurring entities, and metrics disconnected from investigation capacity.

Formulating the event

Define a prediction timestamp and label window. At time t, the model may use account, device, merchant, and transaction information known at or before t. A chargeback or confirmed investigation outcome that arrives later belongs to the label, never to the feature snapshot.

risk_t = model(x_transaction_t, history[:t], graph_snapshot[:t])
label = confirmed_fraud_in_window(t, t + horizon)

Fraud labels are delayed, noisy, and selected by investigation policy. Track label maturity and avoid treating every unlabeled recent event as a negative example.

Temporal features

Useful features describe velocity and deviation: count and amount in rolling windows, time since the last device or beneficiary change, geographic distance, merchant novelty, and deviation from a user's historical profile. Point-in-time feature generation should be reproducible from an event log so a training row can be replayed exactly.

Heavy-tailed amounts and counts benefit from log transforms, robust clipping, and explicit missingness indicators. Feature freshness is part of the contract: a 24-hour-old risk aggregate may be acceptable for batch underwriting but unsafe for card authorization.

Graph-based detection

Fraud is relational. Construct a heterogeneous graph with typed nodes such as accounts, cards, devices, IPs, merchants, and beneficiaries. Edges represent transfers, logins, shared devices, or address relationships. Graph features can include neighborhood counts, connected-component statistics, temporal motifs, and community risk.

Graph neural networks aggregate messages across neighbors, but temporal leakage is easy: a graph built from the full dataset lets a historical transaction observe future edges. Build snapshots as of the prediction time, or use temporal message passing with event timestamps. A simple graph baseline should be measured before introducing a GNN; many fraud gains come from correct relational features rather than model complexity.

Evaluation and calibration

Random cross-validation is usually invalid because the same entities recur. Use forward-chaining windows, an embargo around label periods, and a final untouched time range. Report precision at investigation capacity, recall at a fixed alert rate, PR-AUC, expected financial loss, and calibration. A strong AUROC can coexist with a useless top one percent ranking.

Separate the probability estimate from the action policy. A calibrated score can trigger review, step-up authentication, or a block depending on current thresholds, customer friction, and available investigators. Monitor subgroup performance and false-positive cost; aggressive blocking can create a different business failure from missed fraud.

Real-time serving

The online path needs an event store, low-latency feature retrieval, a versioned model server, and an idempotent decision record. Cache features with explicit freshness bounds. Return a reason code backed by feature evidence, not an invented explanation. If an upstream feature is unavailable, use a declared fallback and record that degraded mode.

Replay production events through the model during incident analysis, but protect sensitive financial data. Monitor p99 latency, feature freshness, score distributions, alert rate, approval rate, drift, and delayed outcomes. A fraud model is healthy only when its ranking remains useful under changing attacker behavior and its decisions remain explainable to investigators.
